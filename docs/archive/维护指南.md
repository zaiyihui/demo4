# 项目维护指南

---

## 1. 目的与范围

本指南旨在规范 Computer Companion（电脑伴侣）项目的文件组织结构、编码规范、测试规范及维护流程，确保代码库保持清晰、可维护和易于扩展。

**平台定位**：
- 本项目定位为 **Windows-only** 桌面应用，所有硬件监控、ETW FPS 采集、皮肤系统、GPU 风扇曲线等功能均依赖 Windows 平台 API（ETW、WMI、LibreHardwareMonitor、NVAPI 等）
- 跨平台抽象层（`IPlatformService`）仅作为接口预留，不保证在 macOS/Linux 上的功能完整性；相关文档中的 macOS/Linux 列仅作设计参考，不应作为支持承诺

**适用范围**：
- 所有项目成员
- 新加入的开发人员
- 代码审查和重构活动
- 版本发布前检查与定期维护任务

## 2. 目录结构规范

### 2.1 标准目录

| 目录 | 用途 | 内容类型 |
|------|------|----------|
| `Models/` | 数据模型 | 业务数据类、枚举、DTO |
| `Services/` | 核心服务 | 业务逻辑服务、数据处理 |
| `ViewModels/` | 视图模型 | MVVM 视图模型类 |
| `Views/` | 用户界面 | XAML 视图和代码后端 |
| `Assets/` | 静态资源 | 图标、图片、字体、皮肤资源 |
| `docs/` | 项目文档 | 设计文档、用户手册 |
| `Tests/` | 测试代码 | 单元测试、集成测试 |
| `Localization/` | 本地化资源 | `Strings.zh-CN.cs` 等多语言字符串 |
| `Styles/` | 样式资源 | `GlobalStyles.axaml`、`SettingsStyles.axaml` |

### 2.2 禁止目录

| 目录 | 原因 |
|------|------|
| `Common/` | 过于模糊，应按功能细分 |
| `Utils/` | 应命名为 Helpers 或 Utilities |
| `Lib/` | 依赖应通过 NuGet 管理 |
| `Debug/` | 临时文件，不应提交 |

## 4. 编码规范

### 4.1 C# 代码风格

| 元素 | 规范 | 示例 |
|------|------|------|
| 类名 | PascalCase | `HardwareMonitorService` |
| 方法名 | PascalCase | `GetCpuUsage()` |
| 参数名 | camelCase | `backupId` |
| 私有字段 | _camelCase | `_logService` |
| 常量 | PascalCase | `DefaultInterval` |
| 接口 | I 前缀 + PascalCase | `ILogService` |

**代码格式要求**：
- 使用一致的 4 空格缩进（由 `.editorconfig` 强制）
- 合理的代码分组，避免过长的行
- 异步操作使用 `async/await`，避免阻塞 UI 线程
- 实现 `IDisposable` 的服务必须正确释放资源

### 4.2 XAML 规范

- 使用 `StaticResource` 引用全局字体与颜色资源
- 控件样式统一在 `Styles/` 目录管理，避免内联硬编码颜色
- 数据绑定优先使用 `CompiledBinding` 以获得编译期检查
- 命名空间对应：`Views/` → `ComputerCompanion.Views`

### 4.3 注释规范

- 公共 API 添加 XML 文档注释（`///`）
- 关键逻辑添加行内注释
- 复杂算法添加说明性注释
- 注释使用中文，与项目默认语言保持一致

## 5. 中文本地化支持

### 5.1 编码与字体配置

- 所有源代码文件使用 **UTF-8 编码（无 BOM）**，由 `.editorconfig` 强制统一
- 控制台输出使用 UTF-8 编码
- 主字体：Segoe UI；中文字体堆栈：`Microsoft YaHei UI, Microsoft YaHei, SimHei, Noto Sans CJK SC, Source Han Sans CN, sans-serif`
- 回退机制：首选字体不可用时自动使用后备字体
- 默认区域：`zh-CN`（简体中文）；支持区域：`zh-CN`、`zh-TW`、`en-US`
- 项目文件（`.csproj`）配置：
  ```xml
  <NeutralLanguage>zh-CN</NeutralLanguage>
  <SatelliteResourceLanguages>zh-CN;zh-TW;en-US</SatelliteResourceLanguages>
  ```
- `App.axaml` 中定义中文字体资源：
  ```xml
  <FontFamily x:Key="ChineseFontFamily">Microsoft YaHei UI, Microsoft YaHei, SimHei, Noto Sans CJK SC, Source Han Sans CN, sans-serif</FontFamily>
  ```

### 5.2 Strings.zh-CN.cs 用法

所有界面文本集中在 `Localization/Strings.zh-CN.cs` 中管理，包括：

- 应用程序通用文本
- 主窗口文本
- 悬浮窗文本
- 设置窗口文本
- 系统托盘文本
- 状态和错误提示
- 单位和格式字符串

引用方式：`Strings.YourStringName`

### 5.3 添加新字符串流程

1. 在 `Localization/Strings.zh-CN.cs` 中添加常量
2. 使用 `Strings.YourStringName` 在 XAML 或代码中引用
3. 如需多语言支持，可扩展为资源管理器（创建 `Strings.zh-TW.cs` 等）
4. 自定义字体：在 `App.axaml` 添加新字体资源，在样式中引用

### 5.4 测试中文支持

1. 编译项目：`dotnet build`
2. 运行程序测试中文显示
3. 检查各种 UI 元素的中文字体渲染
4. 测试中文输入法（微软拼音、搜狗拼音等）
5. 验证特殊字符和标点符号

### 5.5 常见本地化问题

| 问题 | 排查方向 |
|------|----------|
| 中文字符显示为乱码或方块 | 文件编码是否 UTF-8；系统是否安装中文字体；字体堆栈配置是否正确 |
| 中文输入法无法使用 | Avalonia 文本输入控件配置；系统输入法安装；焦点管理 |
| 添加其他语言 | 创建新语言资源文件 → 实现语言切换 → 加载对应资源 |

- **测试项目**：`Tests/` 目录下按服务组织

| 测试文件 | 覆盖率目标 |
|----------|-----------|
| `BackupServiceTests.cs` | 80%+ |
| `LogServiceTests.cs` | 85%+ |
| `PerformanceMonitorServiceTests.cs` | 80%+ |

整体目标：核心服务单元测试覆盖率 ≥ 80%，集成测试覆盖关键业务流程。

### 6.3 测试类别

1. **功能测试**：核心功能正确性、边界条件处理、异常情况处理
2. **集成测试**：服务间交互、依赖注入、配置加载
3. **性能测试**：响应时间、资源占用、并发处理

### 6.4 运行测试命令

```bash
# 编译项目
dotnet build

# 运行所有测试
dotnet test

# 运行特定测试
dotnet test --filter "BackupServiceTests"

# 生成覆盖率报告
dotnet test --collect:"XPlat Code Coverage"

# 集成测试按模块筛选
dotnet test --filter "Integration.BackupRestore"
dotnet test --filter "Integration.Localization"
dotnet test --filter "Integration.Performance"

```

### 6.5 测试用例编写要求

- 测试方法命名：`Method_Condition_ExpectedResult`
- 遵循 AAA 模式（Arrange-Act-Assert）
- 每个测试用例只验证一个行为
- 使用 Moq 隔离外部依赖（硬件、文件系统、网络）

## 7. 新增文件流程

### 7.1 添加新模型

1. 确认模型属于哪个功能领域
2. 在 `Models/` 目录创建文件
3. 命名遵循 PascalCase 规则
4. 添加适当的 XML 文档注释

```csharp
namespace ComputerCompanion.Models;

public class NewModel
{
    // 属性定义
}
```

### 7.2 添加新服务

1. 评估服务职责是否单一
2. 在 `Services/` 目录创建文件
3. 命名格式：`{功能}Service.cs`
4. 实现 IDisposable（如需要）

```csharp
namespace ComputerCompanion.Services;

public class NewService : IDisposable
{
    // 服务实现
}
```

### 7.3 添加新视图

1. 在 `Views/` 目录创建 XAML 文件
2. 创建对应的代码后端文件
3. 确保视图名称与视图模型对应

```
Views/NewWindow.axaml      # XAML 定义
Views/NewWindow.axaml.cs   # 代码后端
```

### 7.4 添加新视图模型

1. 在 `ViewModels/` 目录创建文件
2. 继承 `ObservableObject`
3. 使用 `[ObservableProperty]` 特性

```csharp
namespace ComputerCompanion.ViewModels;

public partial class NewWindowViewModel : ObservableObject
{
    [ObservableProperty]
    private string _title = "新窗口";
}
```

## 10. 代码组织原则

### 10.1 单一职责原则

每个类应只有一个修改原因：

```
✅ 好的设计：
- HardwareMonitorService.cs：仅负责硬件监控
- SettingsService.cs：仅负责设置管理

❌ 不好的设计：
- HardwareAndSettingsService.cs：同时负责多个不相关功能
```

### 10.2 依赖方向

```
Views → ViewModels → Services → Models

不应有反向依赖！
```

### 10.3 命名空间对应

| 文件位置 | 命名空间 |
|----------|----------|
| `Models/` | `ComputerCompanion.Models` |
| `Services/` | `ComputerCompanion.Services` |
| `ViewModels/` | `ComputerCompanion.ViewModels` |
| `Views/` | `ComputerCompanion.Views` |

### 10.4 架构设计原则

本项目遵循 SOLID 原则：
- **单一职责**：每个服务专注单一功能
- **开闭原则**：对扩展开放，对修改关闭
- **里氏替换**：子类可以替换父类
- **接口隔离**：使用小而专的接口
- **依赖反转**：依赖抽象而非实现

模块之间通过接口通信，最小化依赖关系；所有核心功能支持单元测试，使用依赖注入提高可测试性。

## 12. 常见问题处理

### 12.1 循环依赖

**问题**：Service A 依赖 Service B，Service B 又依赖 Service A

**解决**：
- 提取公共接口到新文件
- 使用依赖注入解耦
- 考虑合并相关服务

### 12.2 跨层引用

**问题**：View 直接引用 Model

**解决**：
- 通过 ViewModel 中转
- 保持 MVVM 架构层次

### 12.3 大类文件

**问题**：单个文件超过 500 行

**解决**：
- 按功能拆分为多个类
- 使用 partial class（视情况）
- 提取独立功能到新类

## 15. 性能监控面板测试与实施说明

### 15.1 面板架构

```
PerformanceDashboardWindow (View)
    ├── PerformanceDashboardViewModel (ViewModel)
    │   ├── IPerformanceMonitorService (数据源)
    │   ├── IHardwareMonitorService (硬件数据)
    │   └── ILogService (日志记录)
    ├── 实时指标卡片
    ├── 数据可视化图表
    ├── 告警提示区域
    └── 历史数据查询
```

### 15.2 核心文件

| 文件 | 说明 |
|------|------|
| `Views/PerformanceDashboardWindow.axaml` | UI 界面定义（~400 行） |
| `Views/PerformanceDashboardWindow.axaml.cs` | 代码后台（~50 行） |
| `ViewModels/PerformanceDashboardViewModel.cs` | 视图模型（~350 行） |

### 15.3 实时监控指标

| 指标 | 显示内容 | 更新频率 |
|------|---------|---------|
| CPU | 使用率、温度、状态 | 1 秒 |
| GPU | 使用率、温度、状态 | 1 秒 |
| 内存 | 使用率、已用/总计 | 1 秒 |
| FPS | 帧率、响应时间、错误率 | 1 秒 |

### 15.4 告警规则

| 告警规则 | 触发条件 | 严重程度 |
|----------|---------|---------|
| HighCpuUsage | CPU > 90% 持续 30 秒 | Warning |
| HighGpuTemperature | GPU 温度 > 85°C 持续 60 秒 | Error |
| HighMemoryUsage | 内存 > 90% 持续 60 秒 | Warning |
| LowFps | FPS < 30 持续 10 秒 | Warning |
| CriticalTemperature | CPU 温度 > 95°C 持续 10 秒 | Critical |

告警颜色：🔴 Critical / 🟠 Error / 🟡 Warning / 🔵 Info

### 15.5 历史数据查询

- **时间范围**：15 分钟、30 分钟、1 小时、6 小时、24 小时
- **数据存储**：内存中保存最近 1000 个数据点
- **刷新机制**：手动刷新按钮

## 16. 新功能维护说明

> 本节描述项目新增功能的测试与维护要点，供维护人员参考。

### 16.1 ETW FPS 监控

**功能说明**：通过 Windows ETW（Event Tracing for Windows）采集实时帧率，用于游戏/全屏应用性能监控。

**维护要点**：
- ETW 会话需以管理员权限启动；权限不足时应回退到性能监控面板的 FPS 卡片显示"不可用"，不得崩溃
- 会话生命周期必须正确管理：启动时开启 session，退出时 `Dispose` 释放，避免残留内核会话
- 数据更新频率与性能监控面板保持一致（1 秒）
- 测试场景：游戏全屏、窗口化游戏、桌面空闲，验证 FPS 数值合理（游戏场景应 ≥ 30，桌面空闲应接近显示器刷新率）

**故障排查**：
- FPS 始终为 0：检查 ETW 会话是否成功启动、是否以管理员权限运行
- 数值明显异常：确认未与其他性能监控工具（如 MSI Afterburner）的 RTSS 钩子冲突

### 16.2 皮肤系统

**功能说明**：支持界面皮肤/主题切换，皮肤资源存放于 `Assets/` 目录。

**维护要点**：
- 皮肤资源文件统一放置在 `Assets/Skins/` 下，命名遵循 `{皮肤名}.json` 或 `{皮肤名}.axaml`
- 切换皮肤时必须完整卸载旧皮肤资源，避免资源字典堆叠导致内存泄漏
- 颜色/字体资源通过 `StaticResource` 引用，不得硬编码
- 新增皮肤流程：
  1. 在 `Assets/Skins/` 创建皮肤资源文件
  2. 在皮肤管理服务中注册
  3. 测试所有视图在新增皮肤下的渲染（重点关注对比度、可读性）
  4. 更新皮肤选择列表

**测试检查**：
- 切换皮肤后所有窗口（主窗口、悬浮窗、设置窗口、性能面板）样式一致
- 重启应用后皮肤选择持久化
- 默认皮肤在 Windows 10/11 下渲染正常

### 16.3 GPU 风扇曲线（FanControl）

**功能说明**：支持自定义 GPU 风扇转速曲线（对应服务/模块名 `FanControl`），依赖 NVAPI（NVIDIA）或厂商 SDK。

**维护要点**：
- 仅支持 NVIDIA 显卡（通过 NVAPI）；非 NVIDIA 设备应明确提示"不支持"并禁用相关控件，不得尝试写入
- 风扇曲线修改需谨慎，写入前应校验曲线单调性，避免因异常曲线导致硬件损坏
- 必须提供"恢复默认曲线"与"恢复自动控制"按钮，确保异常时可回退
- 退出应用或卸载时，必须将风扇控制交还 GPU 固件自动管理，避免残留手动控制状态
- 需要管理员权限；权限不足时给出明确提示

**测试检查**：
- 默认曲线加载正确，图形化显示与数据一致
- 自定义曲线可保存、加载、删除
- 重启应用后曲线配置持久化
- 应用异常退出后，风扇恢复自动控制（可通过重启后查看 GPU 状态确认）

## 17. 风险评估

| 风险项 | 等级 | 影响 | 缓解措施 |
|-------|------|------|---------|
| 内存泄漏 | 中 | 性能下降 | 定期检查、资源跟踪、`ResourceCleaner` |
| 安全漏洞 | 高 | 数据泄露 | 输入验证、安全审计、日志脱敏 |
| 依赖过时 | 低 | 兼容性问题 | 定期更新、版本锁定 |
| ETW 会话残留 | 中 | 系统资源占用 | 严格 Dispose，异常退出后检查 |
| GPU 风扇控制异常 | 高 | 硬件损坏 | 曲线单调性校验、提供回退、退出交还控制 |
| 皮肤资源泄漏 | 低 | 内存占用 | 切换时完整卸载旧资源字典 |
